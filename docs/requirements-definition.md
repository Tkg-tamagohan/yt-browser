# yt-browser 要件定義書

mpv による軽量な再生とローカル完結のデータ管理を一体化した YouTube 専用ブラウザ（専ブラ）の要件を定める。
協議で確定した個別の判断は [decision-records.md](decision-records.md) に記録し、本文書からは「仕様決定 A」のように参照する。

## 1. 背景と目的

汎用ブラウザと拡張機能の組み合わせによる視聴環境を置き換える、YouTube 専用のデスクトップクライアントを作る。

主目的は次の三点である。

- メモリ効率が高く、低レイテンシで軽快に動作するクライアントの実現
- Google アカウント不要のローカル完結型フィード、履歴、お気に入り管理
- チャンネルブロックと強力な NG フィルター、SponsorBlock 連携、コマ送り

## 2. 用語

- **専ブラ**：特定サービス専用のクライアントアプリの通称で、本書では YouTube 専用クライアントを指す
- **InnerTube**：YouTube が内部で使う非公開の JSON API で、本アプリではライブチャットと関連動画の取得に限定して利用する
- **継続トークン**：InnerTube が差分取得のために返す不透明トークンで、次回リクエストにそのまま回す
- **SponsorBlock**：動画内の提供読みなどの区間をクラウドソーシングで共有するサービス
- **コマ送り**：一時停止状態でフレーム単位に前後へ移動する操作
- **キュースタック**：セッション限りの一時プレイリストで、任意の動画行から積み上げて連続再生する
- **チャットリプレイ**：終了済みライブ配信のアーカイブで、投稿時刻を動画の再生位置に同期させて流すチャット表示

## 3. 対象環境

- OS：Linux（デスクトップ）と Windows を第一対象とし、macOS は後フェーズとする（仕様決定 G）
- 配布物の Linux 側の動作下限は Ubuntu 24.04 相当以降とし、release ビルドを `ubuntu-24.04` に固定して維持する（仕様決定 AI）
- 必須外部依存：mpv（システムインストール）と yt-dlp（同梱または自動更新、技術方針 P）[^jsruntime]
- 想定ユーザー：個人利用（マルチユーザーや複数端末同期は対象外）

[^jsruntime]: yt-dlp は 2025-10-22 のリリースで YouTube の動画解読に Deno など外部 JS ランタイムを必須化する方針を告知しており、同梱方針は設計書で扱う。

## 4. 機能要件

### FR-1 動画再生

- mpv プロセスを JSON IPC で制御して再生する（仕様決定 B）
- 画質選択：1080p などのプリセットに加え、AV1 や VP9 の優先、fps 指定を含むフォーマット式を設定可能にする
- 再生操作：再生、一時停止、シーク、音量、再生速度、字幕（mpv の機能に委譲）
- PiP とマルチビューは複数 mpv インスタンスの並行制御で実現する。再生の既定表示は PiP とする（FR-18、仕様決定 AJ）

### FR-2 コマ送り

- 一時停止中にフレーム単位で前進と後退ができる（仕様決定 D）
- 入力は mpv 窓上のホイールとキー（`,` / `.`）、アプリ側 UI の双方を受け付ける
- ホイールの既定割り当ては「一時停止中＝コマ送り、再生中＝音量」とし、設定で変更可能にする

### FR-3 購読フィード

- チャンネルの購読登録とカテゴリ（フォルダ）による分類
- バックグラウンドの新着ポーリングはチャンネル RSS を使い、API キーやクォータに依存しない
- 新着動画は未読として一覧に積み、個別既読と一括既読を提供する

### FR-4 検索と関連動画

- YouTube 検索 UI を設け、結果から再生、購読、ブロックへ遷移できる（仕様決定 H）
- 関連動画は InnerTube `next` の小規模クライアントで取得し、チャットと同じ InnerTube 基盤を共用する

### FR-5 チャンネルブロック

- ブロックしたチャンネルの動画をフィード、検索、関連動画から除外する（仕様決定 E）
- 未購読チャンネルもブロック可能にし、管理は一覧からのブロック操作と設定画面での解除で行う

### FR-6 ライブチャット

- InnerTube `get_live_chat` の継続トークンポーラーでリアルタイム表示する（仕様決定 F）
- 表示種別：本文、スーパーチャット、メンバーシップ通知、削除済みメッセージ
- NG 機能：本文と投稿者 ID、投稿者名への literal / regex フィルタ（FR-9 と同一エンジン）
- チャットメッセージはライブ・リプレイとも DB に保存しない（仕様決定 AV）
- 終了済み配信のチャットリプレイは FR-24 で対象とする（仕様決定 AQ）

### FR-7 ローカルデータ

- 視聴履歴と再視聴導線
- 視聴履歴は直近 10000 件を保持上限とし、超過分は最古のものからアプリ起動時に自動削除する（仕様決定 AV）
- 再生位置のレジューム（前回位置から自動再開、手動で先頭再生も可能）
- お気に入りとカスタムプレイリスト

### FR-8 SponsorBlock

- skip 対象カテゴリ（sponsor、intro、outro、selfpromo など）を設定可能にする（技術方針 N）
- 再生位置が登録区間に侵入したら自動でスキップし、UI に一時通知を出す

### FR-9 NG フィルタエンジン

- 対象（動画タイトル、概要文、チャンネル名、チャット本文、投稿者）とマッチ方式（literal / regex）の組み合わせでフィルタを定義する（技術方針 M）
- フィルタは UI から追加、有効化、削除できる

### FR-10 プレイリストの取り込みと連続再生

- YouTube プレイリストの URL をローカルプレイリストへ取り込める（仕様決定 R）
- プレイリストに連続再生の開始点を設け、現在項目の終了に合わせて次項目を自動で再生する
  同一インスタンスで次項目へ切り替え、既定では末尾到達で停止する（仕様決定 S）
  ループは FR-16 を参照
- 再生順はその時点の項目順に従う

### FR-11 プレイリスト項目の並べ替え

- 項目を任意の順序に並べ替えて保存できる
  操作は行の「上へ」「下へ」ボタンとドラッグ＆ドロップの双方を提供する（仕様決定 T）
- 投稿日時の昇順（古い順）への一括並べ替えを提供し、`published_at` を持たない項目は末尾に置く（仕様決定 Z）
- 現在の項目順を反転する一括の逆順化操作を提供し、YouTube が新しい順で返すプレイリストを投稿日時の昇順へ変えられるようにする（仕様決定 Z）
- 並べ替え結果は `playlist_items.position` の更新として保存する

### FR-12 再生中チャンネルの購読

- プレイヤーカードから再生中動画のチャンネルを購読登録できる
- チャンネル ID は既知データ（videos / watch_history）を優先し、無ければ yt-dlp で解決する（仕様決定 U）
- 購読済みはボタンを無効化して「購読済み」と表示し、ブロック中のチャンネルは購読可でブロックは維持する（仕様決定 U）

### FR-13 フィード管理 UI の拡張

- フィード画面を 2 カラム構成にし、左に購読管理（入力と登録リスト）、右にフィード一覧を配置する
- 購読チャンネル一覧をカテゴリ別にフィルタできる
- フィード一覧を種別（live / short / video）でフィルタできる
  `videos.kind` は shorts を新規投入時に非同期で判定して付与し、live / upcoming の検出は初版の対象外とする（仕様決定 V）

### FR-14 画質設定の拡張

- PiP で起動するインスタンスの既定画質を通常再生とは別に設定できる
  新設 `pip.quality.format`、未設定は `quality.format` に従う（仕様決定 W）
- 稼働中のインスタンスごとに画質を変更できる
  変更値はセッション内に限り有効とし、DB には保存しない（仕様決定 X）

### FR-15 アプリの更新

- tauri-plugin-updater で新バージョンの確認、ダウンロード、適用を行う（仕様決定 AB）
- 起動時に自動で更新確認を行い、新バージョンの検知時は確認ダイアログを出し、承認後にダウンロード、インストール、再起動する
- 設定画面に手動の更新確認ボタンを設ける
- 対象バンドルは AppImage（Linux）と NSIS（Windows）とし、deb/rpm は自動更新の対象外とする
  deb/rpm はパッケージ管理に委ねて配布を続ける。MSI は配布しない（Windows 配布は NSIS に一本化、仕様決定 AK）
- 更新情報は GitHub Releases の `latest.json` で配信する

### FR-16 ループ再生

- プレイヤーカードにループボタンを設け、「なし」「プレイリスト全体」「1 項目」の 3 状態を切り替える（仕様決定 AA）
- プレイリスト全体ループは連続再生キューの末尾到達時に先頭項目へ戻り、キューが無い再生では現在項目を繰り返す
- 1 項目ループは単独再生かキュー実行中かを問わず現在項目を繰り返し、キュー中は次項目へ進まない
  キュー位置の進行は、継続再生が次項目か現在項目の繰り返しかを区別して行う
- 各周回を独立した再生として扱い、履歴は動画ごとの既存行をその都度完了として更新する（周回数の行は増やさない）
- ループ継続時は終了のトースト通知のみを抑制し、キュー進行を担う `player://ended` イベント自体は発行を続ける

### FR-17 Chrome 拡張「yt-browser で開く」

- カスタム URL スキーム `yt-browser://` で外部からアプリを起動し、起動中のインスタンスへも URL を渡せる（仕様決定 AC）
- MV3 の Chrome 拡張をリポジトリ内 `extension/` に置き、YouTube の動画画面やプレイリスト画面での拡張実行と、リンクの右クリックメニューから yt-browser で開く
- 拡張から開くときは、Chrome の外部アプリ確認ダイアログを出さず、新規タブも開かない（仕様決定 AH）
  拡張は Native Messaging でアプリ本体のホストモードへ URL を渡し、ホストが `yt-browser://` URL を開く
  ホスト定義はアプリ起動時に自己登録する
- ホストが使えない場合（アプリを一度も起動していない、登録先のパスが無効など）は従来のスキーム方式で開き、確認ダイアログが出るタブをアクティブで開く
  失敗時のみ拡張アイコンのバッジとツールチップで理由を示す
- 対象ブラウザは Chrome とする（Edge と Chromium 系ブラウザは残課題）
- アプリ側は受け取った URL を解析して動画なら再生、プレイリストならローカルプレイリストへ取り込む
  `watch?v=...&list=...` の複合 URL は動画として扱う
- 拡張のストア公開は後フェーズとし、当面は未パッケージ読み込みで運用する

### FR-18 再生の既定表示モード

- すべての再生経路は既定で PiP 小窓（最前面・枠なし）で開始する（仕様決定 AJ）
- 既定表示は設定 `pip.default`（`on`/`off`）で切り替え可能とし、`off` で従来の通常窓を既定に戻せる
- `play_video` の `pip` 引数は省略時に `pip.default` で解決し、明示の `true`/`false` は強制 PiP・強制通常窓として既定に優先する
- PiP 既定では `pip.quality.format` がほぼ全再生の起動画質式として機能する（解決順は FR-14 のまま変更しない）

### FR-19 PiP 窓のアスペクト比追従

- PiP 小窓のサイズを動画の表示アスペクト比へ追従させる（仕様決定 AL）
- `pip.geometry` の WxH は上限枠として扱い、比率を保った内接サイズへ調整する。位置指定（±x±y）は従来どおり
- 追従の有無は設定 `pip.fit_aspect`（`on`/`off`、既定は `on`）で切り替える
- PiP 化、再生中の比率変化、連続再生・ループの項目遷移でも追従が継続する

FR-20 以降は 2026-10 の拡張要求で確定した要件であり、実装計画の Phase 28 以降で実装済み。フェーズ分解は [implementation-plan.md](implementation-plan.md) を参照する。

### FR-20 キュースタック（一時プレイリスト）

- フィード、検索、関連動画、ライブラリの各動画行から、セッション限りのキューへ動画を追加できる（仕様決定 AM）
  追加操作は「キューに追加」（末尾へ積む）と「次に再生」（実行中は現在項目の直後、未実行は先頭へ挿入）の 2 種とし、同一動画の重複登録を許す
- 追加は積み上げるだけで再生は開始しない。キューの「再生」操作で先頭項目から連続再生を開始する
- キューの一覧と編集はナビのキュー入口と、キューを背負うプレイヤーカード内のパネルの双方から行える
  操作は並べ替え（上下ボタンとドラッグ＆ドロップ）、個別削除、全消去を提供する
- 実現は連続再生キュー（FR-10）と同じ機構に統合し、一時キューはプレイリスト未所属（`playlist_id` を持たない）のキューとして扱う
  追加先はプレイリストの連続再生キュー実行中でも常に一時キューとする（「実行中キューへの追記」は仕様決定 AS で改訂、FR-26）。ループ状態（FR-16）はキューのインスタンスにそのまま適用される
- キュー項目の表示メタ（タイトル、チャンネル名、サムネイル）はセッション内メモリに持ち、DB には保存しない
- 同一動画を隣接して登録した場合、継続先の項目が現在項目の繰り返しと `video_id` 基準で区別できず、キュー位置の表示がずれうる（連続再生機構の queue drift と同じく、仕様上の制約として許容する）

### FR-21 チャンネル別フィード表示と過去動画バックフィル

- 購読チャンネル一覧のチャンネル名をクリックすると、そのチャンネルの RSS を即時に再取得し、フィード一覧をそのチャンネルに絞って「未読のみ」を外した状態で表示する（仕様決定 AN）
- フィード一覧のフィルタにチャンネル指定を追加する（1 件。チャンネル指定時はカテゴリ絞り込みを解除する）
- チャンネル絞り込みの表示中は「このチャンネルの過去動画を取得」ボタンで、yt-dlp の flat-playlist によりチャンネルの `/videos` と `/streams` タブの投稿一覧を遡って取り込める
  1 回の取得は各タブ直近 100 件を上限とし（暫定値）、「さらに読み込む」でタブ別の取得済み位置から続きを取得する
- バックフィル項目は `videos` に既読（`is_read=1`）で投入し、既存行は書き換えない
  ただしライブラリ登録などで作られた `ingested=0` のプレースホルダ行は、バックフィルで取り込まれた時点で既読のまま `ingested=1` に確定し、フィード一覧に現れるようにする
  `/videos` 由来は `kind='video'`、`/streams` 由来は `kind='live'` とする。タブ別の取得済み位置はチャンネルごとに永続化する
- 新規投稿で取得位置がずれて重複取得しうるが、`video_id` の冪等で吸収する（既知の制約）

### FR-22 コマ送り時の無音化

- コマ送り（`frame-step` / `frame-back-step`）の操作中は音声を出力しない（仕様決定 AO）
  mpv 窓上のホイールとキー（mpv 標準の `,` / `.` キーバインドを含む）、アプリ側 UI の双方の経路に適用する
- 常時有効とし、設定項目は持たない。ユーザーのミュート状態はコマ送り前後で保持する

### FR-23 フィード一覧の shorts 既定非表示

- 設定 `feed.show_shorts`（`on`/`off`、既定・未設定は `off`）を新設し、設定画面にチェックを置く（仕様決定 AP）
- `off` のとき、フィード一覧の「すべて」と「video」選択は `kind='short'` の項目を除外する
  種別フィルタで「short」を明示選択した場合は表示する
- FR-21 のチャンネル別表示にも同じ規則を適用する

### FR-24 終了済み配信のチャットリプレイ

- 終了済みライブやプレミア公開のアーカイブを再生したとき、チャット欄の表示操作でリプレイを再生位置に同期して流す（仕様決定 AQ）
  表示はライブと同じチャットパネルを共用し、ライブかリプレイかは自動判定する
  （実装メモ：watch 応答の継続トークン種別では終了済みでもライブ系しか出ないため、放送窓 `liveBroadcastDetails` の `isLiveNow`/`endTimestamp` で判定する。リプレイ系継続が直接出る経路も併せて受理する）
- 各メッセージの動画内時刻と mpv の再生位置を照合して流し、シーク時は近接時点へ再アンカーする
- チャットメッセージはライブ・リプレイとも DB に保存しない（仕様決定 AV）。NG 判定はライブと同じエンジンで表示に適用する
- プレミア公開で配信開始と映像開始がずれる場合のオフセットを補正する
  補正量の推定方式は実装で調査し、推定不能な場合は未補正で警告を出す

### FR-25 一覧のページング

- 検索結果、フィード一覧、プレイリスト項目の各一覧末尾に「さらに読み込む」ボタンを設ける（仕様決定 AR）
- 検索は `ytsearch` に継続が無いため、件数上限を段階的に増やして再取得し、既表示に差分だけを追記する
- フィード一覧は投稿日時と動画 ID のカーソルで次の 500 件を追記する
  投稿日時が NULL の項目は末尾側にまとめ、同時刻の並びは `video_id` で安定化する（カーソルの境界判定もこの順序に従う）
- プレイリスト項目は `position` の範囲で分割して取得・追記する
- 履歴一覧は対象外とし、現行の件数上限を維持する

### FR-26 複数キュー

- キューは一時キュー 1 個（`playlist_id` を持たない）と、プレイリストごとに最大 1 個のキューを同時に保持できる（仕様決定 AS）
  各キューは項目列、現在位置、実行インスタンスを独立に持つ
- 複数のキューが別々のインスタンスを背負い、同時に連続再生できる
- 「キューに追加」「次に再生」は実行中キューの有無に関わらず常に一時キューへ入る（FR-20 の追記先を改訂）
  プレイリストキューへ後から項目を追加する経路は持たない
  項目を増やすにはプレイリスト側へ追加してからキューを作り直す
- プレイリストキューは連続再生の開始時点の項目列をスナップショットとして持つ
  開始後のプレイリスト編集はキューに反映されず、キュー側の並べ替えや削除もプレイリストに影響しない
- プレイリストキューの寿命は次のとおりとする
  - 「連続再生を止める」でインスタンスを外してもキューと現在位置は残り、キューパネルの「再生」で保存位置から再開できる
  - 末尾まで再生し切った終端（`player://ended` の `reason=eof`）では位置を先頭に戻してキューを残す
  - それ以外の終端（`quit`・`stop`・`error`・`process_exit` などによるインスタンス消失）ではキューを消滅させる
  - 全消去、対象プレイリストの削除、「ここから連続再生」による新しいキューでの上書きでも消滅する
- 停止済みキューが残っているプレイリストで「ここから連続再生」を選んだ場合は、既存のキューを破棄して新しいスナップショットのキューで上書きする
- 一時キューの寿命は現行どおりとする
  「連続再生を止める」で項目だけ残り位置は先頭に戻り、消費完了とインスタンス消失と全消去のいずれかで消滅する
- キューパネルは上部で表示対象のキュー（一時キューと存在するプレイリストキュー）を切り替え、選択中のキューの一覧と編集を行う
  キューを背負うプレイヤーカードは自分のキューを選択状態でパネルを開く
- ループ状態はインスタンス単位のままとし、キューの帰属に関わらず既存の振る舞いを変えない
- キューと表示メタはセッション内メモリのみで DB には保存せず、アプリ再起動で消える
- queue drift など既存の制約は継承する

### FR-27 ライブチャットのポップアップ

- チャット表示をアプリ本体のウィンドウとは別の OS ウィンドウ（ポップアップ）へ切り離して表示できる（仕様決定 AT）
  ポップアップは通常装飾のウィンドウで、mpv 窓（PiP 含む）より手前へ置ける
- ポップアップは既定で最前面で開き、窓内のピンボタンで最前面の ON/OFF を切り替えられる
  最終状態は設定 `chat.popup_ontop`（`on`/`off`、既定・未設定は `on`）に保存し、次回の起動に引き継ぐ
- 起動は埋め込みチャットパネルの見出しにある「ポップアップ」ボタンから行う
  ポップアップを開いたインスタンスの埋め込みパネルは閉じ、ポップアップを閉じてもパネルは自動で再開しない
- ポップアップは動画単位に 1 窓とし、同一動画への再度の起動は既存窓をフォーカスする
  リプレイ（FR-24）の同期先は起票したインスタンスとする
- ポップアップ内の「パネルに戻す」ボタンで、ポップアップを閉じて起票元インスタンスの埋め込みパネルを開き直せる
  起票元インスタンスが消えている場合は無効化する
- プレイヤーインスタンスの終了後もポップアップは残る
  ライブは配信終了まで流れ続け、リプレイは同期先の喪失で送出が止まる既存の扱いのままとする
- ポップアップの表示行は投稿時刻と本文のみとし、投稿者名と superchat / membership のバッジは表示しない（仕様決定 AU）
- ポップアップの位置とサイズは既定値で開き、初版では保存しない
- 表示内容、NG 判定、削除済み表示、表示件数上限は埋め込みパネルと同一のポーラー経路を共用する
  コメント投稿は対象外とする（仕様決定 H）

## 5. 非機能要件

- メモリ目安：アイドル 300MB 未満、再生中 600MB 未満とする（仕様決定 I）
  初期の目標値であり、計測して見直す。
- 取得失敗の扱い：フィード・チャットの取得不能は UI に状態として明示し、空データを正常と誤認させない
- UI 言語：日本語（i18n 基盤は初期から入れ、英語リソースは後回しでよい）
- 配布：AppImage（Linux）と NSIS（Windows）。deb/rpm も手動配布物として出すが MSI は配布しない（仕様決定 AK）。自動更新は FR-15 に従う（仕様決定 AB）

## 6. スコープ外

- Google アカウント連携の全機能（評価、投稿、メンバー限定コンテンツ、購読の同期）（仕様決定 H）
- 動画ダウンロード機能（仕様決定 H）
- macOS 対応（仕様決定 G）

## 7. 修正要求と調査項目

### BG-1 Windows でチャット欄を開くとアプリ本体が終了する

- Windows 版でプレイヤーカードの「チャット欄を表示」を押すとアプリ本体のプロセスが終了する実機報告がある
  mpv は存続し本体のみが落ちる
  修正後は Windows 実機で再現しないことを受け入れ条件とする（仕様決定 Q）

### INV-1 Windows 11 自動 HDR との連携可否

- Windows 11 の自動 HDR に mpv の表示経路を認識させられるかを調査する
  Windows 環境での調査を先行し、可能なら設定項目として組み込み、不可なら対象外として記録する（仕様決定 Y）

### BG-2 PiP 中の自動再生が時々途切れる

- PiP での再生中に自動遷移が時々途切れる実機報告がある
  対象は連続再生キューの自動遷移とループ（FR-16）の継続の双方とする
  Windows 実機での調査を含めて原因を特定し、修正後は PiP の有無に関わらず自動遷移が継続することを受け入れ条件とする（仕様決定 AD）

### BG-3 再生失敗時の可観測性と周辺修復

- ユーザーの自端末で bot wall（`Sign in to confirm you're not a bot`）に当たり、全動画の再生失敗・履歴タイトルの `watch?v=<ID>` 化・フィード RSS の連続 500・ログ未生成という複数症状が出た実機報告がある
  失敗通知の強化、履歴タイトルの修復、`t=`/`start=` パラメータ対応、ログディレクトリの事前作成などの周辺修復を行う
  Windows 実機での `t=` 指定再生と失敗通知の目視確認を受け入れ条件とする（仕様決定 AF）

### INV-2 Windows 11 自動 HDR への mpv オプションによる対応可否

- ユーザーの自端末で自動 HDR へ対応できていないことが調査前の状況として確認済みとする
  INV-1（仕様決定 Y）の結論の再確認を含めて、mpv 側の HDR 関連設定全般を洗い直し、mpv オプションで対応可能かを調査する
  Windows 実機での調査を先行し、対応可能なら設定項目として組み込み、不可なら対象外として決定記録へ記録する（仕様決定 AE）
  HDR 対応ディスプレイが無い部分は未検証として残す

  【決着】mpv オプション引数で対応可能。仕様決定 Y で導入済みの汎用追加引数 `mpv.extra_args` でユーザーが実機で解消したと報告があったため、新規の設定項目は追加せず `mpv.extra_args` を解決経路とする（仕様決定 AE）

## 8. 制約とリスク

- YouTube の仕様変更への追従が運用の前提になる。
  ストリーム解決は yt-dlp に委譲して更新で追従し、InnerTube の自前部分（チャット、関連動画）は安定度の高い層に限定してモジュール隔離する。
- PO Token：環境や IP 次第でストリーム取得に PO Token を要求される事例が報告されているため、導入手順にプロバイダ設定を含める（技術方針 P）
- SSAI：広告のサーバーサイド挿入が全面化した場合に、動画広告を構造的に除外できなくなる可能性がある。
  現状は mpv 経路でほぼ遭遇しない認識だが、広告区間検出の要否として継続監視する。
- 規約面：ストリームの直接取得は YouTube 利用規約上グレーゾーンであり、個人利用かつ非営利の範囲で運用する前提を明記する
